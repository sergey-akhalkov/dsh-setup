# Workflows

`@dsh-setup/plugin-workflows` has two halves in one row (`dsh-setup-workflows`):

- the read-only **observability** surface from `add-workflow-observability` — a per-session event journal, a shadow trigger catalog, a run projection, health, the read API, and the Workflows view;
- the **obligation engine** from `add-workflow-obligations` — stored definitions, deterministic triggers, durable runs, evidence-verified steps, and the gates that refuse a turn close or an `openspec` creation/archive while a required step is open.

Disabling the row removes both halves together. The plugin contributes two surfaces: the session **Workflows** tab (one status line, a `Workflows` overview with a page per workflow, and the session's `Runs` feed with one run's detail page) and the right-sidebar **Workflow design** page (a workbench with the workflow rail, the building blocks, the editor canvas, the inspector, and a secondary `Diagnostics` disclosure for the trigger catalog and the receipts), opened from its Start guide card. The engine never adds a second event log: every trigger evaluation goes to the same journal and is rendered inline beside the event it evaluated.

## Definition schema

Definitions are closed-schema JSON data under `.dsh/workflows/definitions/*.json` (local), the package's read-only `assets/definitions/*.json` (engine-shipped), or a read-only contribution from an installed plugin. The schema is versioned (`v: 1`) and every unknown field, duplicate step id, dangling edge, implicit cycle, or credential-shaped value fails load with the definition and field.

Top-level fields: `v`, `id` (lowercase kebab, also the install file name), `name`, an optional `description` (human-readable text of at most 500 characters, never used by the engine), `version`, `trigger`, `settings`, `steps`.

`settings`: `allowModelStart`, `risk` (`low`/`medium`/`high`), `gateOwnership` (`own`/`defer`, default `own`), `maxBlocks`, `allowIntent`, `allowTools` (the tool allowlist), `legacy` (`{plugin, signal}`, required for a deferred definition), and the optional closed `gate` (`intake`) that selects an engine-owned pre-execute gate.

A step has `id`, `title`, `executor` (`main`, `subagent`, `tool`, `branch`, `loop`, `human`), optional `prompt`, an `evidence` completion contract, `next` (a step id or `end`), optional `blockTurnClose`, `nonCritical`, `ownership`, `legacy`, and the executor-specific object. A `branch` step declares `branch: {predicate, then, else}`; a `loop` step declares `loop: {maxIterations (≤50), stop, next, cap}` and must be the only way to iterate. An `all` evidence contract is a non-empty recursive list, passes only when every item passes, and its failure names the first failing item path (`items[0].items[1]`).

Installed definitions: the engine ships `task-review`, `retro`, and `verify` as the remaining legacy-retirement exceptions (the setup keeps their legacy switches off); `@dsh-setup/plugin-openspec` contributes `change-intake` (active, own, `settings.gate: "intake"`, with the `spec-review` step deferred to the strict `spec-review` rule) when the engine's registry service is available.

### Definition registry

An installed plugin contributes read-only definitions and shadow triggers through the host `workflowsDefinitions` service; the plugin waits for it with `ctx.inject` and registers nothing when the engine is absent. The engine never scans package directories, reads a plugin's package files, or accepts a profile path list. Every contribution is validated with the same closed definition and trigger schemas before any part of it is registered; a duplicate definition or trigger id is refused naming both sources, and a disposed plugin's contribution is removed while the runs it recorded stay readable. The editor and API expose the source as `shipped`, `plugin:<plugin name>`, or `local`; a plugin definition is read-only and editing one creates a workspace-local copy.

## Triggers

Deterministic kinds the engine may evaluate: `turn.stopping`, `tool.pre-execute`, `tool.result`, `fs.change`, `subagent.end`, and `review.record`; the optional intent trigger is a separate kind, never a deterministic event. The observability shadow catalog keeps its six kinds (agent turn start/stop, tool result, subagent start/end, workspace file change); the engine's extra kinds and outcomes are additive and documented by the `workflow-observability` delta.

A trigger is `shadow` or `active`, with a `dedupe` policy (`none`, `turn`, `path+content-hash`, `callId`, `name`) and optional `repeat` and `applicability` (`checkpoint-required`). A shadow match records `would-fire` and acts on nothing. An active match starts at most one run per dedupe key (a repeat starts a new run). A not-applicable trigger records `not-applicable` and creates no run. The retro applicability is the workflows row's `checkpointApplicability` config: `minToolCalls` (default 4) and `requireWrite` (default true). The plugin cannot read another row's config, so the operator MUST mirror the installed goal-continuity checkpoint settings there; a mismatch makes retro start or stay idle when the legacy checkpoint gate would not. The workflow page's evaluation history shows the effective vocabulary inline beside each event: the shadow reasons (`would-fire`, `event-mismatch`, `filter-mismatch`, `dedupe`, `disabled`, `not-ready`, `error`) plus the engine outcomes `run-created`, `run-suppressed`, and `not-applicable`; only an evaluation that carries a run id renders a run link.

The optional intent trigger is shadow by default, records the classifier name, confidence, and reason, and can start a run only when both the plugin row's `config.allowIntent` (default false) and the definition's `settings.allowIntent` are true and the definition was installed and user-confirmed. The host classifies the latest user message with the bounded built-in heuristic (`heuristic-v1`); a definition matches only its declared `intent`, `classifier`, `session`, and `workspace` filters.

A deterministic trigger's `match.command` is a template with at most one `{name}` placeholder (for example `openspec new change {name}` or `acme deploy {name}`); a `match.path` glob may carry one whole-segment `{name}` (for example `openspec/changes/{name}/tasks.md`). Before matching, the engine strips at most one documented `rtk` or `pnpm exec` invocation prefix, collapses whitespace, unquotes one symmetric quote pair around the captured name, and rejects a compound command. The captured name reaches the run context as `name` and is the subject of the `name` dedupe policy; the observed event carries the raw command and path. An empty, repeated, or unclosed capture fails definition validation with the field, and a trigger without a capture behaves as before. The archive gate's `openspec archive` and move parser is the documented engine exception: it keeps its OpenSpec archive/move knowledge until the archive and receipt behavior moves with the remaining definitions.

## Evidence

A critical step never completes from a model text claim. The completion contract is one of:

- `file` — a workspace-relative path, existence, non-empty, optional `minBytes`, optional segment glob; a link or `..` escape is refused.
- `record` — the whole-spec review at `.dsh/delegation/spec-review/<change>/spec.json` or the portable task record at `openspec/changes/<change>/reviews/<taskId>.json`, matched on rule/change/phase/scope/task/verdict and, with `digest: current`, the current change artifact digest; a task-scoped record never satisfies a whole-spec step. A `source: checkpoint` record reads a goal-continuity checkpoint.
- `tool` — a completed tool call with the declared name and arguments.
- `check` — a foreground shell result that ran after the step was requested with exit 0 and no timeout, signal, or sandbox denial.
- `human` — a recorded user answer matching the declared accepted answer.
- `all` — every recursive item; the first failure is reported with its item path.
- `declaration` — only for a `nonCritical` step; it is recorded as `self-declared` and never satisfies a critical step.

## Host authentication

Approvals (`.dsh/workflows/approved.json`), completion/adoption receipts (`.dsh/workflows/receipts/<change>.json`), and authoritative run files are signed with HMAC-SHA256 using a host key at `~/.dsh-setup/workflows-host.key` (or `DSH_WORKFLOWS_HOST_KEY`). The loader and archive gate verify the signature: an unsigned, forged, or modified approval, receipt, or run is refused after reload and cannot authorize a creation, archive, resume, or receipt. Editing an installed definition changes its hash and refuses it until re-approved.

Trust boundary: the key gives tamper-evidence against model-mediated writes (`write`/`edit`/tool paths there are refused by the pre-execute guard), accidental edits, and on-disk tampering between host restarts. It is **not** a boundary against an arbitrary same-user shell or `run_code` program, which can read files the host can read; that case is outside this threat model. Approvals and receipts are durable across restarts but are not tamper-proof against the OS user.

The engine never loads `.dsh/workflows/drafts/`; a model may propose a draft, and only the user-started `/workflows install <path>` or the design page's save copies, validates, and approves it. The editor saves through the same exported host `installDefinition` function: the definition bytes and their matching HMAC approval are persisted together, a failure restores both, and a successful editor save is therefore an authorized install, never a model activation. The install path refuses a linked ancestor or a destination outside the definitions directory. A local override that shadows an installed definition with a declared pre-execute gate cannot remove or weaken that declaration: the loader refuses it with a reapproval remedy naming the missing `settings.gate` and the retired `<name>` token, the installed definition stays effective, and the user re-saves a copy from the installed template and approves it.

## Session view

The Workflows tab is the session's automation overview and run history. One status line carries the listener state with its counts and last error available on demand, then two segments in this order: `Workflows`, the overview of the installed definitions, and `Runs`, the session's all-runs feed.

`Workflows` groups the installed definitions by the trigger kind each definition records, one section per kind. A section shows its kind, its bound workflows with each definition's own mode and filter, and the group's firing count as the sum of those definitions' `definition:<id>` evaluation counts (`matched/total`). A kind with no base catalog trigger still renders from its definitions; a kind with no bound workflows states so and shows no counter. Each workflow row shows its name, version, risk, and source (`shipped`, `plugin:<name>`, or `local`), its `completed / total` runs (completed over every recorded run, so unfinished work is never hidden), and separate `failed`, `running`, `cancelled` and `interrupted` counts; `blocked` joins `running` when non-zero, and the latest run is listed too. Every row is a keyboard-accessible button.

Selecting a workflow opens its page: the definition's description, version, risk and gate ownership; a read-only node canvas of the trigger and ordered steps with a run-overlay selector (the latest run by default; choosing an older run changes only the overlay and never opens the run detail); the ordered architecture chain as a table below the canvas, each step with its executor and next, branch or loop target; the trigger binding with its firing counts; the workflow's runs newest first, where opening a run shows the existing run page and that page's back control returns to the workflow page; and the workflow's evaluation history. The canvas is read-only — a node click selects it for inspection and starts no step, tool, or run — and the ordered step table remains the accessible fallback when the canvas cannot render. The history is scoped to the definition — only its `definition:<id>` evaluations, each beside its event with the event time, matched state and plain reason. Only an evaluation that carries a run id links to its run; a matched evaluation without a run shows its reason and detail instead. The back control returns to the overview and restores its scroll position and focus. `Runs` keeps the session's attributed runs newest first, each row with the composed title, trigger (or the legacy source), a relative start time with the absolute time on hover, status, and duration when the run is terminal. Selecting a run replaces the list with its detail page (definition identity or source, trigger, start and end time, status, steps with their evidence kind and reference or link, failure class, reason, violations, error, and the record link); the back control restores the list's scroll position and focus, or the workflow page when the run was opened there. The view reloads on open, on demand and when the window becomes visible again, re-reads the pages already loaded, and resolves the open run by id; only a confirmed lookup miss says the run is no longer recorded. The tab has no authoring control and performs no write.

**Breaking:** the `Journal` segment is removed. Its session-wide event list moved to each workflow page's definition-scoped evaluation history.

## Workflow design page

The editor lives on the right-sidebar **Workflow design** page, opened from its Start guide-card entry the same way the OpenSpec panel is opened. It is not a mode of the conversation tab, and it edits the same JSON the engine loads. The page is a three-pane workbench: a left column with the building blocks and the installed workflows, the node canvas in the center, and the inspector beside the canvas. The inspector follows the selection: at a pane width of at least 980 px it is the third column; between the shipped 720 px threshold and that width it opens as an overlay drawer over the canvas (from a node selection or the header's details control). The page opens on the selected workflow or, when none is selected, the first installed workflow; with no installed workflow it shows the rail and a blank start surface. The trigger catalog with each last evaluation and the authenticated receipts sit behind a closed-by-default `Diagnostics` disclosure, so the default surface is the workbench and never the old read-only definition table.

- **Workflow rail**: each installed workflow is its own card — name, a two-line description (or an explicit `No description` state), a trigger chip, version/source/step count, and the open definition's latest run with its state dot when loaded. Selecting a card opens that definition; a dirty document asks before it is discarded. The `+` control starts a new definition.
- **Blocks**: the rail lists the six deterministic trigger kinds (as a single choice, with the current one marked) and the six executors (`Agent`, `Tool call`, `Subagent`, `Ask user`, `Branch`, `Loop`), each with its shipped icon and a one-line hint. A trigger block sets the workflow trigger and never adds a step; a step block adds an unconnected node with that executor. A step brick can be clicked or dragged onto the canvas, where the node lands at the drop position; the click path is the keyboard and screen-reader path. The palette is always engine vocabulary, never a list of whole workflows.
- **Canvas**: the trigger node renders first, then the ordered step nodes, then the terminal `end` node, laid out with room between the columns and rows. Nodes are cards with the executor's icon, title, executor label, run-state dot, and a one-line evidence reference (violations stay wrapped). The canvas has a dot grid, zoom and fit controls, and pan, zoom, selection, and focusable nodes and edges. Only the branch and loop edges carry a text label (`true`/`false`, `body`/`exit`); the `start` and `next` edges stay quiet. Drag a node to move it and drag between handles to connect.
- **Layout**: at column widths the rail and the inspector are resizable by dragging their splitters, or with the arrow keys when a splitter has focus (Shift moves further); double-click resets the rail to 280 px and the inspector to 360 px, and the canvas keeps at least 360 px. The remembered widths live in the browser's local storage, so reopening the page keeps them.
- **List mode**: the header's actions menu switches to a form editor with every step field and every edge, backed by the same editor state and save path. When the page's own pane is narrower than the shipped 720 px threshold it opens in List and keeps the canvas one control away; the rail remains above the list (stacked) and the list adds the same executor blocks as an `Add step` menu. The inspector renders inline under the list at that width.
- **Inspector**: the selected node's fields in identity, behavior, evidence, connections, and danger groups, plus the workflow-level `name` and `description` and the settings above them, with the labels and controls sized for the wider remembered column. The description field is the workflow summary the rail and the session workflow page show; clearing it removes the field instead of saving an empty string.
- **Header**: one primary `Save`, the definition name and trigger/source tags, the dirty state with the version, the run overlay as a popup menu (the latest runs with status and version, or an explicit no-run entry), the details toggle at drawer widths, an overflow menu, and `Close`. The overflow menu holds `New definition`, `From template`, `Open draft`, `Reload`, the list/canvas switch, and `Delete`; delete asks in an in-page confirmation banner.
- **Diagnostics**: a secondary, closed-by-default disclosure holding the read-only trigger catalog and receipts. The design page no longer renders a read-only definitions table; the rail and the session workflow page are the definition surfaces.
- **Templates**: the installed definitions (engine-shipped `task-review`, `retro`, `verify`, and a plugin-contributed `change-intake`) are read-only templates; "create from template" copies one into a local definition with a new id and `version: 1`. A plugin template keeps its `plugin:<name>` source label, and an installed definition is never edited or deleted in place.
- **Lifecycle**: a new definition starts at `version: 1`; a copy or duplicate gets `<id>-copy` (then `<id>-copy-2`, …); rename changes only `name`, because the id is immutable; delete removes a local definition and is refused while an active run references it, returning the run ids.
- **Save is an authorized install**: the host validates the graph with the engine's own `loadDefinition` schema, writes the definition and its matching host-signed approval together, and returns the new revision (the SHA-256 of the exact file bytes). A failed definition or approval write leaves both unchanged. One successful save bumps `version` by one.
- **Create-only and revisions**: every definition and layout write sends `expectedRevision`. A create-only save sends `null`; the host creates atomically, and a collision returns `409` with the current revision and writes nothing. Update and delete send the revision from the read that loaded the resource; a mismatch returns `409` with the current revision and writes nothing, and the editor offers reload, the next free id, or save-as-copy. Definition and layout revisions are independent: the first layout save sends `null`, and neither save requires the other's revision.
- **Layout sidecar**: node positions live in `.dsh/workflows/layout/<id>.json` as `{v: 1, id, positions: {[stepId]: {x, y}}}`. They never enter the definition, the engine ignores the file, and a missing sidecar uses a deterministic layered layout, so a missing or stale layout cannot change a run.
- **Run overlay**: the page selects the newest run for the open definition (`source=workflow&definition=<id>`), or another run of that definition from a selector that labels each run with its id, status, and recorded definition version, and overlays each node with the recorded state, structured evidence (`kind` and `ref`, with the full ref in the tooltip), producer-owned failure class, and violations. The accessibility summary notes when the run's recorded definition version differs from the open definition. A run step the definition no longer has is marked orphan and never drawn as a node; a definition step missing from the run shows no run state; a violation naming an unknown step is a run-level notice. The overlay is read-only: a node click opens the property panel, and it never starts a run, a step, or a tool.
- **Drafts**: a definition draft is `.dsh/workflows/drafts/<name>/definition.json`. It is never loaded and never listed as a local definition; opening it in the design page and saving it installs it through a create-only, approved save at `version: 1`. The user's save is the confirmation.
- **Close guard**: an explicit tab close with unsaved edits asks first through the sidebar's close-handler seam; a declined prompt keeps the tab open.
- **Accessibility and fallback**: a screen-reader summary states the trigger, step count, selection, and run state; the block bricks, the `Add step` menu and the keyboard connect path (select a source, press `C`, choose the labelled target) replace drag; focus is visible. A canvas render error switches to List with a bounded notice and the definition stays editable; the host, the session view and the runs are unaffected. A client-module evaluation failure happens before render and is reported by the Harness loader, outside this in-view fallback.
- **Bundle budget**: the design page adds the pinned `@xyflow/react` (12.12.1) as a static import inside the existing single `lib/client.js`; there is no lazy chunk and no second canvas artifact. That one-artifact requirement is the documented reason for a larger budget than the original 250 KB uncompressed estimate: after the workbench redesign (React Flow's `Background`/`Controls` and the shipped brick icons included) the esbuild bundle is 655,719 bytes (the shipped artifact is 717,643 bytes once the loader wrapper indents it; minified 341,780 bytes, gzip 99,732 bytes). `test/canvas-budget.test.ts` records these numbers and enforces bundle <648 KiB, minified <352 KiB, gzip <128 KiB, and artifact <712 KiB. Shortcut: revisit the 250 KB budget when the shared build minifies clients or permits a canvas chunk.
- **Trust boundary**: the editor writes only `.dsh/workflows/definitions/` and `.dsh/workflows/layout/`; the workspace comes from the live session, ids are validated, and links or escapes are refused. Conditions are JSONLogic data, never evaluated in the client, and a credential-shaped definition is refused by the host validator.

## Runs

Each run is one JSON file under `.dsh/workflows/runs/<runId>.json`, replaced atomically on every transition. Statuses: `running`, `blocked`, `completed`, `failed`, `cancelled`, `interrupted`. A run is scoped to one session and one workspace; another session can view it but cannot satisfy its steps. On startup an unfinished run becomes `interrupted` with a bounded reason and is never auto-completed. When the owning session ends, its `running` and `blocked` runs are marked `interrupted` the same way; the advance path records that ended identity and replaces a stale in-flight advance with the interrupted state instead of reviving the run. `/workflows resume <runId>` (or the `workflows` tool `resume`) re-evaluates an `interrupted`, `blocked`, or `failed` run's pending step without recreating a change directory or starting a second run; a failed step is reopened with its evidence, reason, failure class, and attempt count cleared. Runs execute one requested step at a time, and one start per dedupe key. The active-runs system-prompt section lists only the requesting session's runs.

A `task-review` run settles its `start-review` step from an existing matching PASS/ERROR record instead of dispatching `delegate`; a run whose checked task id no longer exists in the change's `tasks.md` is cancelled as superseded before its next advance, and a restored task starts a fresh run. A failed tool dispatch is retried at most three times across turn closes; after the cap the run becomes `failed` (terminal), the failed-dispatch refusal stops, the completion-coverage check still refuses a final tick without a portable PASS, and `resume` or `cancel` is the recovery.

Retention: terminal runs are pruned after 30 days or when the workspace exceeds 20 MB; open runs are retained. Receipts are separate files and survive pruning while the change exists, so an archive authorization is not revoked by pruning.

## Gates

- **Turn close** (`agent/turn-stopping`, root turns only): while a run has an open `blockTurnClose` step that the engine owns and does not defer, the gate steers with the step prompt, its evidence contract, and the exact workspace-relative path the verifier checks. Refusals are bounded by `maxBlocks`; after the cap the close is allowed exactly once with a visible `VIOLATION` in the run and is never reported as a pass. An internal error fails open. Subagent turns are exempt.
- **Pre-execute intake** for a shell command that matches an installed definition's `match.command` template and declares `settings.gate: "intake"` (the contributed `change-intake` template is `openspec new change {name}`; the bare, `rtk`, and `pnpm exec` forms normalize to the same match): an authenticated completed run of that definition or an authenticated receipt allows the call without starting or resuming anything; an owned `create-change` call is allowed; a resumable intake for the name resumes at its pending step and the call is refused; an existing `openspec/changes/<name>/` without a resumable run or receipt is redirected to `/workflows adopt <name>`; otherwise the intake run is created and the call is refused with its first step. The gate's running, resumable, and completed-run lookups use the selected definition id, never a fixed one. A compound command is not matched; the archive gate and the change watcher are the backstop.
- **Pre-execute archive** over `openspec archive <name>` and over a move of `openspec/changes/<name>` into `openspec/changes/archive/` through `mv`, PowerShell `Move-Item`, or `git mv`: refused while a related run has an open required step, when no authenticated completed intake run and no authenticated receipt exist, or when the current whole-spec PASS record is missing or stale. A forged/unsigned receipt or run and a text claim never allow it. A command carrying a shell separator that contains an archive invocation or archive move the parser cannot read is refused with the "could not be parsed safely" reason instead of falling through, so `cd x; openspec archive y`, `cd x && openspec archive y`, `git status; git mv openspec/changes/auth "openspec/changes/archive"`, and `cd .; mv openspec/changes/auth openspec/changes/archive; pwd` cannot evade the gate. The check is textual: a mention inside quoted text or a comment is refused too, while a compound command that names no archive proceeds.
- **User-clicked archive** (`workflowsArchiveGate.authorizeAndCheck(workspace, change)`): the OpenSpec panel's `Archive` button is the user's confirmation and the final authorization. The host service ensures the host key, verifies the four change artifacts and the current whole-spec PASS, and writes the host-signed adoption receipt for the click; it then reports success, so an open required run step, a missing portable task-review approval, or a deferred/malformed `openspec/review-approval.json` marker cannot block the user's click. The agent's chat `openspec archive` command keeps the full pre-execute archive gate above. The OpenSpec route then runs `openspec archive <name> --yes` itself, refusing an unsafe CLI-reported name before spawning. A profile without the engine provides no service, and the OpenSpec plugin's own complete-task check still applies.
- **Verification**: the `verify` definition requires a foreground zero-exit result for the profile's `verify.commands` after the last code write, and the agent runs the command, never the definition. A profile with an empty command list (the shipped default) keeps the definition inert: the step records `no-command` evidence and the turn close is allowed without a verification steer.
- **Authorization write guard**: a model-originated write to `.dsh/workflows/definitions/`, `.dsh/workflows/approved.json`, `.dsh/workflows/receipts/`, or `.dsh/workflows/runs/` is refused; only host-owned install/receipt calls pass.

## Commands and tool

User commands:

- `/workflows` — names the Workflows tab as the entry point (a Host command result is text-only and cannot open a client view); nothing starts.
- `/workflows run <definitionId>` — user-started run.
- `/workflows resume <runId>` — resumes an interrupted, blocked, or failed run.
- `/workflows install <path>` — validates, asks the user, copies into the definitions directory, and records the hash + host signature.
- `/workflows adopt <name>` — verifies an existing change's four artifacts and the current whole-spec PASS record, asks the user, and writes the adoption receipt without recreating the directory or calling `openspec new change`.
- `/workflows status` — bounded text summary.

The `/workflows` command definition carries `input.hint` (`run <definitionId> | resume <runId> | install <path> | adopt <name> | status`), the documented placeholder for capable clients: without it the composer treats the command name as complete and Tab/Enter runs it before the user can type `adopt <name>`. The handler and its accepted argument forms are unchanged.

The model tool `workflows` offers `list`, `start`, `resume`, `status`, `evidence`, `cancel`, and `adopt`. It refuses a raw script or definition, a start without `allowModelStart` (and a high-risk start without a direct user yes), a resume in another session, and unauthenticated runs, an unverified evidence claim, and an install. `adopt` requests adoption of one existing change: the host asks the user in the question UI and writes the same host-authenticated receipt only after a yes; the model cannot supply the answer, and no receipt is written for a no, a timeout, or an unavailable question service. `cancel` also accepts a run whose owning session has no live agent, because no agent can satisfy it. `list` names a definition with `allowModelStart: false` as user-started, never as a refused model start. The tool never writes an approval, and the only receipt it can cause is the user-confirmed adoption receipt.

## Intake flow

1. `openspec new change auth` is refused and an intake run starts.
2. The agent writes `.dsh/workflows/drafts/auth/requirements.md`, then `architecture.md`, then `interface.md`; each turn close re-checks the same path the steer shows.
3. `create-change` runs the owned `openspec new change auth` call and completes only from that call plus the created `.openspec.yaml`.
4. `spec` verifies the four artifacts and `openspec validate auth --strict`; strict validation lives here, after creation.
5. `spec-review` is deferred: it reads `.dsh/delegation/spec-review/auth/spec.json`, requires the current whole-spec PASS, and dispatches no `delegate` call; the legacy strict gate remains the only steer.
6. `approval` asks the user; only a yes completes the run, writes the host-authenticated `.dsh/workflows/receipts/auth.json`, and lets the archive gate accept the change later.

A restart after `create-change` marks the run interrupted; the next `openspec new change auth` resumes it at `spec` without recreating the directory or being redirected to adoption.

## Migration and rollback

A change created before the row was installed is adopted with `/workflows adopt <name>` or the `workflows` tool `adopt` action: the host verifies `proposal.md`, `design.md`, `tasks.md`, at least one `specs/*/spec.md`, and the current whole-spec PASS record, asks the user, and writes the adoption receipt. The model may request the adoption, but the confirmation answer and the receipt are the host's.

While a legacy gate is installed, a step covering the same behavior declares `legacy: {plugin, signal}` and `ownership: defer`; it reads the legacy record, dispatches no executor, and adds no second steer. A deferred definition or step refuses to load when its source is not installed (naming `retire-legacy-gates`), and an `own` step refuses to load while its declared source is installed. `task-review`, `retro`, and `verify` ship active and `own` with their legacy source recorded; they create observational runs and enforce their own gates, and the setup keeps the corresponding legacy switches off.

Rollback: set the row `enabled: false` (stops new runs and steers, keeps records) or remove the row. The legacy gates keep enforcing, so rollback removes no guarantee.
