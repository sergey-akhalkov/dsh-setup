# OpenSpec

[OpenSpec](https://github.com/Fission-AI/OpenSpec) is an AI-native system for spec-driven development:
a change proposal carries its proposal, spec deltas, design, and tasks, and the skills walk the agent
from proposal to implementation, spec sync, and archive. Upstream is MIT licensed, copyright (c) 2024
OpenSpec Contributors.

`@dsh-setup/plugin-openspec` packages the six core OpenSpec skills for DeepSeek Harness. It ships the
skills only: the `openspec` CLI is a machine prerequisite, and the setup never installs, pins, or
vendors it.

## What the plugin ships

The catalog lists six on-demand skills, so every session of the profile can use the workflow without
copying files into a project:

- `openspec-propose` — create a change proposal with all its planning artifacts in one step.
- `openspec-explore` — think through an idea before it becomes a change proposal.
- `openspec-apply-change` — implement a change proposal's tasks.
- `openspec-update-change` — revise an existing proposal's planning artifacts.
- `openspec-sync-specs` — merge a proposal's spec updates into the main specs.
- `openspec-archive-change` — archive a finished change proposal.

The propose, update-change, and apply-change bodies also append a short plugin-owned "Task lanes"
addendum before the adapter note. It defines an execution lane as a top-level task group with
disjoint owned paths and fixes the lane shape at plan time: each level-2 heading names its owned
paths, or `tasks.md` states one single-lane reason that is a work constraint — a shared hot file,
generated output, or a serial gate — never the task-review or archive process. Before the first
implementation task, apply reads those headings once and assigns each independent lane to a worker
or records its serial decision, with no new tool or state. Shared files, generated output, and the
full repository gate stay in a serial tail. The explore, sync-specs, and archive-change skills do
not carry it, and no project `openspec/config.yaml` rule is needed.

The full skill bodies load only when the model or a user invokes one; the catalog carries the
descriptions. The plugin writes no files, adds no always-on prompt section, and has no configuration.
A project or user skill with the same name wins over the packaged one, which is why stale local copies
must be removed as described below.

## Prerequisite: the OpenSpec CLI

`openspec` must be on the PATH of the Harness process. Install the release the skills are pinned to:

```sh
npm install -g @fission-ai/openspec@1.15.0
openspec --version
```

Without the CLI, the Harness still starts and the catalog still lists the skills; the first command
fails with a "command not found" error, and the skill's adapter note repeats the install command. A
different CLI release can run the same skill text, but its command surface may drift; this repository
refreshes the skills through a release, never at runtime.

## Specs live in each workspace

The skills keep OpenSpec's project-local model: the nearest `openspec/` root in the workspace owns
its specs and changes. This setup has no global or shared spec root.

- First use in a workspace: run `openspec init --tools none` at the workspace root. That creates
  `openspec/specs`, `openspec/changes`, and `openspec/config.yaml` without installing skills into the
  project.
- Do not run the skill-installing init variant: the skills are already global, and project copies
  shadow the packaged set and drift on every OpenSpec update.
- A workspace that ran the skill-installing init before adopting this bundle has
  `.dsh/skills/openspec-*`. After installing the bundle and restarting the Harness once (so the
  recomposed profile mounts the new row), delete those directories:

```powershell
Remove-Item -Recurse -Force .dsh\skills\openspec-*
```

```sh
rm -rf .dsh/skills/openspec-*
```

After that the six names resolve to the packaged definitions and the workspace root remains the only
per-project state.

## Install

The plugin is part of the full setup bundle, so `install.ps1` or installing `@dsh-setup/setup` from
Discover enables it. To install only this plugin, use its own entry in Discover, or install a
commit-pinned git specification with the application fully quit:

```sh
dsh plugin --profile desktop add "git+https://github.com/sergey-akhalkov/dsh-setup.git#<commit>&path:/packages/plugin-openspec"
```

Use either the full setup or the individual plugin for this package, never both: installing both
mounts the same row twice. Restart DeepSeek Harness after installing so the profile recomposes with
the new row.

## Provenance and updates

The six skill files are generated by the pinned OpenSpec release and committed with their MIT license
and `openspec.lock.json`, which records the upstream repository, version, tag, commit, npm tarball
integrity, generator command and profile, every skill's description, size, and SHA-256, and the
license hash. An offline test verifies those bytes.

The task-lane addendum (`packages/plugin-openspec/assets/guidance/task-lanes.md`) lives outside
`assets/openspec`, so `pnpm openspec:update` regenerates only the pinned set and leaves the addendum
in place. The upstream files and the lock remain the only pinned content.

Refreshing is a repository release step, not a runtime fetch:

```sh
pnpm openspec:update --version X.Y.Z
pnpm gen
pnpm build
pnpm test
```

Review the generated asset and lock diff, then follow [docs/releasing.md](releasing.md). The running
plugin never replaces or extends its vendored upstream content; the task-lane addendum is plugin-owned
and sits outside the pinned set.

## Remove the plugin

Disable the row in the profile's own `cordis.patch.yml`:

```yaml
- id: dsh-setup-openspec
  disabled: true
```

or uninstall the plugin bundle. The workspace `openspec/` root and its content stay in place.
