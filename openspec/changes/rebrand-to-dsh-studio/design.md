# Design

## Context

See `proposal.md` — Why. The current state that shapes the design:

- The repository ships 19 git-installed packages; there is no npm publication, so the scope change
  is an identity change, not a registry migration.
- `packages/setup` is outside the pnpm workspace. Its manifest, patch, and vendored tree are
  generated from the plugin manifests by `pnpm gen`; `lib/**` is generated by `pnpm build`.
- Row ids are global and namespaced by the repository prefix; `scripts/lib/fragments.ts` enforces the
  pattern, and the generator refuses duplicates.
- The market index URL is derived from `dsh.json.repository`; `install.ps1` keeps its own copies of
  the index and repository URLs.
- Installed profiles persist the package name in `dependencies` and `dsh.profile.bundles`, and users
  may persist row ids in their own `cordis.patch.yml`.
- Workflow runs and receipts store the workspace path and reject a different one, and the Hindsight
  bank id is derived from the checkout directory name (`coding-agent::<basename of git root>`); the
  workflow host key lives at `~/.dsh-setup/workflows-host.key`. Both are keyed to the current
  checkout path.

## Goals / Non-Goals

Goals: one consistent identity in every current namespace; one breaking release with a tested
migration guard; generated output reproducible from sources; history untouched.

Non-goals: no npm publication, no alias package, no automatic profile-patch rewrite, no behavioral
change to any plugin, no rewrite of archived artifacts or review records.

## Decisions

### D1: Full rename in one major release

Choose variant A over variant B (identity-only). Rationale: the package name changes in every
installed profile either way, so a second wave would double the reinstall and review cost for no
reduction in risk. The only extra hazard of A is the profile-patch row ids, which is handled by D6.

### D2: Package scope is identity, not distribution

There is no registry step: the market index points at commit-pinned git sources. The rename is
therefore limited to manifests, the vendored path, imports, and tests. The setup manifest's
dependencies and `bundleDependencies` are regenerated from the manifests, so they need no hand edit.

### D3: Row ids follow the scope; historical ids do not

Current fragments, defaults, and validators move to `dsh-studio-*`. The retired adapter rows
`dsh-setup-nuphus-mcp` and `dsh-setup-serena` are ids that exist only in old profile patches; they
stay in the dogfood allowance and the migration requirement. Alternatives: keeping all row ids
(variant B) or emitting alias rows (extra config, no behavior gain); both rejected.

### D4: Prompt-section ids are internal and rename with the bundle

`dsh-setup:ponytail`, `:working-principles`, `:rtk`, `:serena` have no user configuration; the
observability defaults name the same sections. Renaming them keeps the assembled prompt and the
readiness check consistent.

### D5: Server-derived identifiers follow the package name

Skill providers, HTTP routes (`/plugins/dsh-studio-*`, `/api/plugins/dsh-studio-openspec/*`), client
slot ids, command definition ids, and the workflows source label move with the package name. They are
internal; the cost is transient UI state (an open tab may not restore after reinstall).

### D6: The installer refuses a legacy profile and does not migrate it

Detection reads the target profile manifest before any write: a dependency on or selection of
`@dsh-setup/setup` stops the run with the removal-and-rerun action. The installer does not remove the
dependency (non-bundle user state) and does not rewrite the profile patch (documented contract). The
alternative — automatic removal and patch rewriting — would make the installer own user state and
change the published `portable-setup` contract, so it is deferred to a separate decision.

### D7: Keep the workflow host-key path and the checkout directory name

`~/.dsh-setup/workflows-host.key` stays, and the checkout directory keeps its current name. Renaming
the key path would generate a new key, and every existing workflow approval, run, and receipt
verified with the old key would stop verifying. Renaming the directory changes the stored
`workspaceKey`, so existing runs are no longer resumable and their receipts read as absent, and the
Hindsight bank id (derived from the git-root basename) would split. A shortcut comment records the
limit and the upgrade path (a supported workspace-key and bank migration, not this release).

### D8: Rename the installer backup directory

`.dsh/.dsh-setup-backups` becomes `.dsh/.dsh-studio-backups`. Old backups are debris, not read across
runs; the installer only uses its backups within a failed run.

### D9: Release after the repository rename and after the open changes

The code rename lands first; then the owner renames the GitHub repository and verifies Actions,
Pages, and the `raw` installer URL; then the tag `v1.0.0` publishes the first index at the new URL.
The old index URL is accepted as a 404. The new index has no prior versions, which is correct for a
new package identity; `fetch-previous-index.ts` already treats a 404 as the expected first release.

The rebrand lands after the currently open changes archive, because their delta specs name the old
package scope; an old-scope delta synced later would reintroduce the old name into the main specs.
Their mentions are reconciled before the rebrand's sync, and a change that plans a new plugin package
uses the new scope from the start.

### D10: One mechanical pass with a keep-list

The replacement is reviewed against an explicit keep-list:

- archived changes, historical status notes, and review records;
- the retired-row compatibility literals (`dsh-setup-nuphus-mcp`, `dsh-setup-serena`) where they
  appear as old-profile fixtures: `scripts/lib/dogfood.ts`, `scripts/validate-composition.ts`,
  `scripts/test/dogfood.test.ts`, `scripts/test/adapter-guidance.test.ts`,
  `openspec/specs/portable-setup/spec.md`, `docs/install.md`, and `docs/lazy-mcp.md`;
- the preserved host-key path `~/.dsh-setup/workflows-host.key` in
  `packages/plugin-workflows/src/host/host-auth.ts`, its generated
  `packages/plugin-workflows/lib/host-auth.js`, the first-party vendored copy under
  `packages/setup/node_modules/@dsh-studio/plugin-workflows/lib/`, `docs/workflows.md`, and
  `openspec/specs/workflow-observability/spec.md`;
- the legacy-detection and migration literals: `@dsh-setup/setup` in `install.ps1`, its diagnostics
  and tests, the migration section of `docs/install.md`, including the stale row-id example, and the
  `portable-setup` legacy-setup requirement before and after its sync;
- third-party packages under `packages/setup/node_modules`;
- this change's own artifacts, which intentionally name both identities.

Everything else that matches `dsh-setup` or `@dsh-setup` is a defect.

### D11: Version 1.0.0

The rename changes the installed package identity and (for profiles with row overrides) observable
configuration ids. `0.x` would understate that; `1.0.0` is the release line's first stable identity.

## Risks / Trade-offs

- A legacy profile bypasses the guard or the installer is run with an old index → two setups mounted,
  duplicate rows and tools. Mitigation: detection before any write, an installer exercise for the
  refused case, and a release note.
- Old market source and one-line installer stop working → users must re-add the source and rerun the
  new command. Mitigation: documented in the install guide and release notes; the old index 404 is
  intentional.
- A user patch keeps `dsh-setup-…` row ids → overrides silently stop applying. Mitigation: documented
  rule; the installer never edits the patch.
- Renaming the checkout directory later would invalidate workflow authority and split the Hindsight
  bank. Mitigation: the directory is kept for this release; a future rename needs a supported
  workspace-key and bank migration.
- A change in flight still names the old scope in its delta and reintroduces it on sync. Mitigation:
  the rebrand lands after the open changes archive, and their old-scope mentions are reconciled first.
- The scan gate is enforced with a stale keep-list. Mitigation: the keep-list above is the single list
  used by the design and the verification task.
- A blind text pass rewrites history or the retired-row allowance. Mitigation: keep-list and the
  repository-wide scan gate.
- Generated artifacts drift. Mitigation: `pnpm build && git diff --exit-code` and `pnpm gen:check` in
  the release gate.
- Saved client UI state (tabs, panel slots) does not survive the slot-id rename. Mitigation: accepted;
  state is per-session and rebuilds on demand.

## Migration Plan

1. Land the implementation on `main`; run `pnpm build`, `pnpm gen`, and the repository checks.
2. After the open changes archive, reconcile their final text, sync the delta specs into the main
   specs, and run the full gate including the scan gate on the synced tree.
3. Owner renames the GitHub repository; verify Actions, Pages, and the `raw` URLs.
4. Tag `v1.0.0`; verify the new index lists `@dsh-studio/setup` `1.0.0` with a commit pin.
5. Owner machine, with the Harness closed: copy the profile manifest and patch aside, remove the
   legacy setup bundle, run the new installer, and re-add the market source. Keep the checkout
   directory name and the workflow host key.
6. Rollback: restore the copied manifest and patch, then reinstall the pinned legacy commit. The
   installer's own backup covers only its run, not the manual pre-step; the old market index is not
   restorable after the repository rename, which is accepted.

## Open Questions

None that change the specs or the task breakdown. The distribution audience beyond the owner is
unknown; if third-party profiles exist, the documented manual migration covers them.
