# Tasks

The engine spans one Host package plus its Client view; lanes 1-4 own disjoint Host modules and lane 5 owns the Client. The final group is the serial integration tail.

## 1. Definition schema and loader (lane 1, owns `src/host/definitions.ts`, `src/host/approval-store.ts`, `src/host/host-auth.ts`, `assets/definitions/*.json`, `test/definitions.test.ts`)

- [x] 1.1 Define the closed JSON schema for definitions: id, name, version, trigger, settings, steps, executor, evidence, edges, allowModelStart, risk, gateOwnership, per-step ownership and legacy source, maxBlocks. Include the recursive `all` evidence contract with a non-empty item list and first-failure reporting. Verify a valid definition loads, the complete shipped `change-intake` definition loads with its `all` contracts, an unknown field fails, and a duplicate step id or dangling `next` fails with the definition and field.
- [x] 1.2 Implement local definitions under `.dsh/workflows/definitions/`, read-only shipped assets, and the host approval store `.dsh/workflows/approved.json` keyed by definition id and content hash with an HMAC-SHA256 signature made with a host key held outside `.dsh`, including the validated install/approve function used by `/workflows install <path>`. An approved local id overrides the shipped one; an unapproved local file, a forged or unsigned approval, or a file modified after approval is refused; `.dsh/workflows/drafts/` is never loaded. Verify the approved override, read-only shipped definitions, a direct model write refused, a matching definition/approval pair without a valid signature refused after reload, a modification after approval refused, and a model-written draft not being loadable.
- [x] 1.3 Enforce ownership per definition and step: a `defer` step requires its declared legacy source to be installed, an `own` step with a declared legacy source is refused while that source is installed, and a definition may be `own` for its own steps while the `spec-review` step is `defer`. Verify each combination with a fake profile and the shipped strict `spec-review` rule.

## Workflow follow-up

- Install the generated setup in a throwaway profile, attempt `openspec new change` without an intake run, and confirm the refusal, the draft steps, the create-change step, strict spec validation, the whole-spec review PASS, only-yes approval, and the host-authenticated completion receipt.
- Restart after `create-change` and confirm the interrupted intake resumes at `spec` without recreating the directory or adopting.
- Attempt `openspec new change` on an existing change directory with no resumable intake and confirm the `/workflows adopt <name>` redirect.
- Write a definition draft, confirm it is not loadable, install it through `/workflows install <path>`, and confirm it becomes startable; then modify the installed file and confirm it is refused until re-approved; write a forged approval or receipt and confirm it is refused after reload.
- Adopt `add-workflow-obligations` (or another pre-existing active change) through `/workflows adopt`, prune the run history, confirm the authenticated receipt is retained, and archive without recreating the directory.
- Confirm the deferred task-review and retro runs add no second steer while the legacy gates are installed, and that repeated short, read-only, or question-ending turns create no blocked retro runs.
- Archive the change after the project's review requirements are satisfied; do not retire a legacy gate in this change.
