# Proposal

## Why

This setup ships sixteen plugins whose business rules are enforced at runtime by prompt text, tools,
turn-time gates, and injected messages. The owner cannot answer the operational question the setup
exists to satisfy: did a rule actually fire, and is a plugin still working? Nothing surfaces that today
except reading a session by hand through the agent's own session tools.

DSH already stores every session as an append-only event log. A separate telemetry pipeline would
duplicate a second, lossy view of the same facts and drift from the log (this session's own first user
message is already missing from the Chat transcript while present in the log). The missing piece is not
collection; it is a query and view over data that already exists.

## What Changes

- Add a new bundle `@dsh-setup/plugin-observability`: a generic signal engine over session trajectories
  plus an `Observability` view beside `Chat` and `Trajectory`.
- Define a **signal** as a named declarative matcher over session events (event type, tool name,
  injected message source kind, turn-abort reason prefix, command name, one argument value). The
  configuration is pure data; it is never executed.
- Ship built-in signal sets that work on any DSH installation with no configuration: `activity`,
  `tools`, and `errors`.
- Ship the per-plugin view as configuration, not code: plugins that inject messages or abort turns are
  attributed automatically, tool ownership comes from an optional map carried by the setup owner
  defaults, and a prompt-only plugin is declared as a guidance row so it is named rather than missing.
- Count each session's own events once: a continuable child session may start with a copy of its
  parent's log, so the reader starts at the session's durable inheritance boundary.
- Add range selection (`session`, `day`, `week`, `month`) with fixed buckets, aggregates computed on
  demand from the Host session query service, and an in-memory cache. No new storage, no new log.
- Render charts as inline SVG using the published theme tokens: no charting dependency in the client
  bundle.
- Document the signal vocabulary and the view in `docs/plugins.md`, so a community user can add their
  own signal without reading the source.

## Capabilities

### New Capabilities

- `observability`: the contract for deriving activity from session trajectories: the signal matcher
  vocabulary, built-in signal sets, ranges and buckets, the view's presentation rules, what is never
  persisted, how unattributed plugins appear, and which blind spots the view MUST state rather than
  hide.

### Modified Capabilities

- `portable-setup`: the owner defaults now also carry the observability signal map that attributes
  shipped plugins' tools to their owning plugin.

## Impact

- New package `packages/plugin-observability/`: host aggregator and route, client view, locale, icon,
  composition fragment, tests.
- `packages/setup/defaults.yml` changes; `packages/setup/{package.json,cordis.patch.yml,node_modules/**}`
  are regenerated by `pnpm gen`.
- `docs/plugins.md` and the README plugin table gain a row.
- `scripts/lib/generate.ts` picks the new fragment up automatically; no generator change is expected.
- No DSH API change: the Host session query, web server, slot, and theme services already exist. The
  tool registry exposes no plugin owner field, which is why tool attribution is configuration data.
- Out of scope for v1 and stated in the view: prompt-only guidance plugins, load-time failures, UI
  rendering effects, and rule-compliance heuristics over model text.
