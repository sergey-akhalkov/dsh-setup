# Design

## Context

See `proposal.md` for the motivation. The current `lane-boundary` trigger evaluates at turn close, derives a
completion from this session's own `tasks.md` before/after write pair, and settles it with a per-turn
`workerStarted` boolean or one progress note. The boolean is cleared at every turn start, and the note is
read as one change-wide escape. The existing trigger, lane parser, steer payload, and fail-open requirements
are already documented in `openspec/specs/delegation-rules/spec.md`; this change adds a second trigger and
leaves the old one in place for compatibility.

## Goals / Non-Goals

**Goals:**

- Start fan-out at the first implementation tick, not after the first lane is finished.
- Remember assignments across turns so a later lane completion never demands a duplicate worker.
- Make the assignment per lane: one lane assigned or serial does not settle the others.
- Make worker evidence precise enough that an unrelated worker does not settle the gate.
- Keep the existing lane parser, checkpoint payload, worker isolation, and fail-open behavior.

**Non-Goals:**

- No new tool, plugin, contract, or always-on prompt section.
- No automatic merge of a worker branch; the session still merges after its checks.
- No dependency graph between lanes; a dependent lane is either serialized with a note or assigned later.
- No cross-session assignment sharing; the gate stays session-scoped like the rest of the engine.
- No persistence of the ledger to disk; a restart re-arms the decision.

## Decisions

### D1 — Add `lane-assignment`, keep `lane-boundary` deprecated

The new trigger is a different decision point, not a bug fix inside the old one. Keeping `lane-boundary`
accepted avoids breaking a profile that names it in its own rules, and lets the new trigger ship in the
default while the old requirements remain true. The skill and docs mark the old trigger deprecated and point
new rules at the new one. A future change can remove it once no profile needs it.

Alternative rejected: redefine `lane-boundary` in place. It would be smaller, but it silently changes the
meaning of an existing trigger and makes a profile's behavior depend on the setup version without a
configuration change.

### D2 — A session-scoped ledger, not a per-turn boolean

State per change and lane: `assigned`, `serial`, or absent. `assigned` comes from a successful tagged worker
start; `serial` comes from a matching `task_progress` note; `current` is derived from the lanes this session
ticked in the turn and is not stored. The ledger belongs to the existing per-agent `DelegationState`, next to
the failure streak and write evidence, so it is cleared with the session and never crosses sessions.

Why not a workspace file: the gate is already session-scoped, a file would need cleanup and a cross-session
ownership story, and a restart re-arming one decision is harmless. Why not reuse the progress note as the
only state: the note is one record per change and cannot represent several serial lanes.

### D3 — The worker tag is the evidence

The steer prints `lane-tag: <change>#<n>` in every worker prompt. A successful `subagent`, `subagent_fork`,
`spawn_teammate`, or `workflow` result assigns the lane only when its tool arguments contain that exact tag.
The tag is a coordination label, not a secret and not a gate bypass: the worker prompt is generated by the
gate, so normal compliance is one paste.

Alternatives rejected: any successful worker settles the rule (the current behavior; an unrelated worker
settles it); parse the lane title from the prompt (title text is user-authored and can be renamed); count
worker starts only (does not tell which lane).

### D4 — The serial escape is per lane

A successful `task_progress` note for a task in a lane marks only that lane serial, provided its worktree
digest matches at the time of the note. The ledger keeps the decision after the worktree changes, because it
is a plan decision rather than a worktree fact. Other lanes stay unassigned and still gate. The note remains
the existing tool and record; no new note type.

Alternative rejected: keep one change-wide note escape. It lets one serial lane silence the whole change,
which is the failure this change removes.

### D5 — The current lane is the lane ticked this turn

If the session ticked a task in lane A, A is current and is not reported for fan-out; the session is allowed
to keep working there. Every other unchecked non-serial lane without an assignment is reported. If the
session ticked tasks in several lanes, all of them are current for that turn.

Alternative rejected: report the current lane too. It would demand a worker for the work the session is
actively doing, causing a race on the same files and a pointless handoff.

### D6 — Fire on any implementation turn, not only at a completion

The trigger reports whenever the plan has at least two non-serial lanes, the turn ticked a task or changed
implementation files, and an unassigned non-serial lane with unchecked tasks remains outside the lanes ticked
this turn. The lanes ticked this turn are current and are not reported. On the first tick this starts fan-out
early. On later turns an assignment settles the lane, so the rule does not repeat for it; only genuinely
unassigned lanes remain. A plan with exactly one non-serial lane reports nothing. This is the difference
between a per-turn ritual and a state-driven gate: the rule is quiet once the state is correct.

Alternative rejected: keep the completion boundary and add only a first-tick special case. It would still
forget assignments across turns and would still demand duplicates at later boundaries.

### D7 — Reuse the existing payload, list only unassigned lanes

The steer reuses the root-anchored checkpoint commit, the force-add of an ignored change directory, the
one-worker-per-lane `subagent` call, and the no-machine-path rule from the lane-boundary payload. It lists
only unassigned lanes and adds the lane tag to each call. The worker instruction still requires a sibling
worktree and branch and forbids ticking `tasks.md`.

### D8 — Fail open and prune

An unreadable `tasks.md`, no level-2 headings, an unassigned lane without owned paths, or a turn with no
implementation change or tick reports nothing. A lane that disappears or becomes complete loses its
assignment. A renamed lane is a new unassigned lane. The separate soft artifact hint is unchanged.

## Risks / Trade-offs

- **Tag discipline** → If the session writes its own worker call without the tag, the lane stays unassigned
  and the gate repeats. The steer prints the exact call; the serial note is the escape; the skill and tests
  keep the tag in the documented call.
- **A dead worker leaves the lane assigned** → The gate does not spawn a duplicate. The task and
  implementation-work gates still pressure the task, and the session can mark the lane serial or reassign it.
  The trade-off favors no duplicate writers over automatic replacement.
- **A restart loses the ledger** → The gate may fire once for already-assigned lanes after a Host restart.
  The session can reassign; no records or plan state are lost.
- **A lane edited without a tick** → The lane is unassigned and can be reported while the session is editing
  it. The existing task-by-task workflow expects a tick; assigning the lane or ticking the task resolves it.
- **The deprecated trigger keeps its old flaws** → It is accepted only for compatibility and is not in the
  default set. The docs name it deprecated; a future change can remove it.
- **The gate can fire on every turn while an unassigned lane remains** → That is the intended pressure; the
  strict steer gives one paste-ready call per lane and a one-call serial escape. It is not a model call.

## Testing

The plugin tests import the built entry (`lib/index.js`), so the engine lane builds
`packages/plugin-delegation-rules/lib/**` before running them and owns that output. The serial tail runs the
final build and generation after both lanes and verifies the vendored setup tree; it does not replace the
lane's build with a stale one.

## Migration Plan

The shipped `lane-fanout` rule switches to `lane-assignment`; existing profiles that name `lane-boundary`
continue to compose and keep the old behavior. No records, notes, or task files need migration. The ledger
starts empty per session. Release and install are needed for the shipped default to reach a machine; until
then the source tests and the existing gate remain the verification. Rollback is a rule change back to
`lane-boundary`; the new trigger and state can stay inert.
